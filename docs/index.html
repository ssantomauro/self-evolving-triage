Software That Rewrites Its Rules
An experiment with Levanto Sage 2 and Claude

Software that rewrites its own rules

A decision model makes every call. An LLM reads the mistakes and proposes better rules. The software tests each proposal on its own history and keeps it only if it works. Nobody edits the code.

Code and data: github.com/ssantomauro/self-evolving-triage

The idea

Most product logic is a pile of if statements. Someone watches how users behave, decides the rules are wrong, edits the code and ships it. The software only gets smarter when a developer does.

Decision models like Levanto Sage 2 change what that logic can be. Sage takes some content and a question and returns a structured answer with a probability, in milliseconds, for a fraction of a cent. You can call it wherever you'd write an if. The rules it follows are plain-English instructions and definitions, which means they are data.

And data can be rewritten by a program. Pair the decision model with an LLM that reads where the decisions went wrong and proposes new instructions, add a test that only lets better instructions through, and you get software whose behaviour improves from how people use it. This experiment builds that loop and lets it run.

This isn't a benchmark. The point is to show the mechanism working on real data, and to make you think about where else it could live.

The test bed: labelling GitHub issues

I needed a feature where users produce feedback without being asked. Issue triage is a good one: a new issue arrives, the software suggests labels, and a few hours later the maintainers apply the labels they actually wanted. Every issue tells the software whether it was right.

I replayed the real history of five public repositories: pandas, black, pydantic, pip and poetry. That's 6,643 issues in date order, about 12 content labels per repo. Each repo has its own habits that nobody explains to the software. The rule of the replay is simple: decide first, then see what the maintainers did.

Four ways to build the same feature

Every version gets the same issue, in the same order, and must answer before the maintainers' labels are revealed. They differ in what decides and in what, if anything, changes afterwards.

In code, the difference between C and D is small. They share the same Sage request. D adds about 90 lines: a memory of similar past issues, a cutoff per label, and the rewrite step. Here is the whole idea of D's rewrite step, simplified:

every 150 issues:
    proposal = claude.propose(current_spec, recent_mistakes)
    if score(proposal, last_60_issues) >= score(current_spec, last_60_issues) + 0.01:
        current_spec = proposal        # the software changed its own rules
    log(proposal, scores)              # every change is explained and auditable

Claude never labels an issue. Sage makes all 6,643 decisions per version. Claude is called rarely, to think about patterns: 40 times in the whole experiment.

What happened

The comparison that matters is C against D. Same model, same issues, same starting instructions. The only difference is the loop.

Classic ML is a fine way to solve this particular problem, and it ends up close to D. That's expected: issue labelling has thousands of examples and a fixed set of categories, which is exactly what ML likes. What D shows is different. Two things stand out:

  • It's useful from day one. Sage starts from label names and descriptions, so the first 50 issues of each repo are already labelled reasonably. ML has nothing to learn from yet.
  • It handles labels it has never seen. On the first 15 uses of a label the maintainers added partway through, D scores 0.62 F1 and ML scores 0.07. ML needs examples before it can predict a label at all.

Watch it rewrite itself

An accepted rewrite: pip learns its own templates

For its first 160 issues, the pip bot ran on the generic starting instructions. It was too generous: it often added type: enhancement next to type: feature request, and stuck area labels on anything that mentioned them. Claude looked at those mistakes and wrote this:

Maintainers label sparingly: usually exactly one 'type:' label, chosen mainly by issue template. 'Description / Expected behavior / How to Reproduce' issues get 'type: bug', even if the user may be at fault. 'What's the problem this feature will solve?' issues get 'type: feature request'. Add a 'C:' or 'project:' label only when that area is clearly the core subject.

Nobody told it that pip's labels follow its issue templates. It worked that out from the maintainers' behaviour. On the 60 held-out issues the new rules scored 0.78 against 0.58, so they went live. The very next issues show the difference:

A rejected rewrite: poetry almost forgets what it learned

At issue 160, the poetry bot had learned that its maintainers almost never apply area labels at triage. Around issue 960, Claude saw a batch of recent mistakes where some area labels had been used, and proposed bringing them back:

Live rules

Area labels are applied very rarely at triage; default to NO area label even when the topic seems related (solver, venv, cli, deps, sources, etc.).

Proposed

Then add area labels for the subsystem where the failure clearly lies; multiple areas may apply (e.g., solver+sources+vcs).

On the next 60 issues the maintainers barely used area labels, and the proposal would have added wrong ones everywhere. The test scored it 0.60 against 0.92 for the live rules, and the software kept what it had. This is the part that makes running without a human acceptable. The LLM can have a bad idea. The software checks every idea against its own data before trusting it.

What it cost

  • Sage: about $5.50 for every decision in the experiment, around 16,900 of them including the pilot and every proposal test. That's about $0.0003 per decision.
  • Claude Opus 5.5: 40 calls, one per proposal.
  • Infrastructure: none. No training pipeline, no labelled dataset to prepare, no model to host. The learner is about 140 lines of Python.

Because every decision is cheap, the software can afford to re-run the past. That's how the test works: before trusting new rules, it replays 60 recent issues with both versions and compares.

Where else this pattern fits

Issue labelling is just a convenient place to watch it. The pattern needs three things: a decision the software makes often, a signal users produce anyway that shows whether it was right, and rules that can be written in plain language. Plenty of products have all three.

ProductDecision Sage makesSignal users produce anywayWhat rewrites itself
Support deskWhich team gets this ticketWhich team finally solves itRouting rules per team

ModerationRemove, warn or allowAppeals that succeedThe policy definitions
Expense toolApprove or send to reviewWhat finance overturnsThe approval policy
InboxUrgent or laterWhat the user opens firstThat user's idea of urgent

In each case the work splits the same way. The decision model makes thousands of fast, cheap calls. The LLM makes a few slow, thoughtful ones about what the patterns mean. A plain test decides which ideas survive. And because the rules are text, every change can be read, explained and rolled back.

Limits

  • The loop is only as good as its signal. A repo whose maintainers don't label gives it nothing to learn from.
  • The test uses 60 recent issues. That catches bad ideas like the poetry one, but close calls can go either way.
  • This is a replay of history, not a live product, and five Python repositories are a small world.

Run it yourself

Everything is in the repository: the four versions, the replay harness and every decision each version made, including the full log of rewrite proposals. Each version is a short file in triage/bots/.

make install && make fetch      # download the issue histories
make classic                    # versions A and B, free
export SAGE_API_KEY=...         # plus ANTHROPIC_API_KEY for version D
make sage && make report
